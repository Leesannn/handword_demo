# 팀 발표 진행안

10~12분 발표를 가정한 초안입니다. 팀의 공식 발표 시간과 팀원 이름을 반영해 조정합니다.

## 발표 흐름

| 순서 | 시간 | 화면·자료 | 설명 |
|---|---|---|---|
| 1 | 1분 | 앱 이름·다섯 단어 | 초보자의 본보기 따라 하기와 기록 수집이라는 목표 |
| 2 | 1분 | 실제 앱 번역·학습 화면 | 사용자가 시작·판정·재시도를 경험하는 흐름 |
| 3 | 1분 | README 아키텍처 | 단말 추론과 학습 데이터 수집이 연결되는 구조 |
| 4 | 2분 | 좌표→모델 도식 | 59점·177값·30프레임, 기기별 추론 구현 |
| 5 | 2분 | 요청→적재 시퀀스 | Outbox, 202 응답 시점, Kafka 키, 원장 이벤트 ID |
| 6 | 1분 | 두 계정 네트워크 | PrivateLink, Internal NLB, TLS·인증, 탄력적 IP |
| 7 | 1분 | 인덱스 전후 표 | 문서 검사 73→10, 원문과 순서 동일 |
| 8 | 1분 | 실제 검증 표 | 두 아이폰 동시 사용, Android 적재, 재송신 관찰 |
| 9 | 1분 | 후속 작업 | Spark 집계 복구, 좌표 샘플 통합, 모델 평가 |

## 역할별 설명 포인트

### 앱·추론 담당

카메라에서 손·몸 좌표를 뽑아 같은 전처리 규격으로 단어를 판정합니다. iOS는 Core ML, Android는 JavaScript GRU를 사용합니다. 기록은 먼저 폰에 보관하며 같은 event_id를 유지해 다시 보냅니다. 기기별 UI 차이와 모델 임시 기준을 설명합니다.

### 메인 서버 담당

FastAPI는 인증·배치·이벤트 필드를 검증하고 Kafka 발행 확인 뒤 202를 반환합니다. Spark는 체크포인트 기반으로 소비해 원장과 통계를 저장합니다. 오프셋으로 누락을 찾고 별도 배치로 재처리한 사례를 설명합니다.

### DB·연결 담당

별도 계정의 MongoDB를 PrivateLink와 TLS로 연결하고, 앱 event_id와 Kafka 오프셋을 원장에서 대조했습니다. 최근 기록 조회에서 전체 스캔이 발생하는 것을 확인해 복합 인덱스를 추가했습니다. 검사 문서는 73건에서 10건으로 줄었고 반환된 원문은 같았습니다.

## 실제 시연 순서

1. 담당자는 API·Kafka·Spark·MongoDB의 실행 상태와 접속을 사전 확인합니다.
2. DB에서 현재 토픽·파티션·오프셋 기준점을 기록합니다. 현 원장에 partition이 없으므로 Kafka 측 정보와 함께 관리합니다.
3. 폰 두 대에서 서로 다른 단어로 연습을 시작합니다. 폰별 event_id와 HTTP 응답을 확보합니다.
4. Kafka에서 두 ID의 파티션·오프셋을 확인합니다.
5. MongoDB에서 같은 ID와 원문, 사용자·세션을 확인합니다.
6. 집계 컬렉션·계산 정의가 확인된 경우 해당 창의 스냅샷을 함께 보여줍니다.

DB에 아직 도착하지 않았다면 API 응답, Kafka 발행, Spark 소비·필터·출력 대상 순서로 확인합니다. 같은 이벤트를 재송신했다면 전체 건수 증가 대신 해당 ID의 존재와 원문을 대조합니다.

시연 중 콘솔에는 API 키·비밀번호·개인키를 표시하지 않습니다. 동시 시험의 성공은 특정 두 단말 시나리오의 결과로 설명합니다.

## 예상 기술 질문

| 질문 | 답변 요점 |
|---|---|
| 서버가 수어를 추론하나요? | 제공 앱은 기기 내 추론을 사용하며 서버는 이벤트 수집·집계를 수행 |
| 왜 iOS와 Android 엔진이 다른가요? | Core ML과 WebView 실행 환경 차이. 동일 전처리·가중치 계산의 기준값 대조 필요 |
| 177과 30은 무엇인가요? | 59개 점의 XYZ와 고정 길이 시간 입력. 단어 모델 입력은 30×177 |
| 확률 0.6이면 정확도 60%인가요? | 확률 출력과 실측 정확도는 다름. 0.6은 현재 표시용 임시 기준 |
| 영상도 서버에 저장하나요? | 영상은 기기에서 처리. 이벤트와 별도 좌표 샘플 계약 존재 |
| 202를 받으면 DB 저장까지 끝났나요? | Kafka 발행 확인 뒤 수락하며 DB 저장은 비동기 후속 처리 |
| 재전송하면 통계가 두 배가 되나요? | 원장 키 중복 방지와 집계의 재실행 보장을 구분. 실제 Spark 중간 실패 검증은 후속 |
| 원장은 무엇인가요? | 개별 이벤트를 보관하고 재처리·집계 대조의 기준으로 삼는 컬렉션 |
| 왜 payload를 문자열로 보관했나요? | 원문 보존에 활용. 사용자·기기 검색에는 파싱이 필요해 검색 모델 개선 여지 존재 |
| 인덱스 효과는 어느 정도인가요? | 이 시험에서 문서 검사 73→10. 시간은 0~1ms라 속도 개선률로 환산하지 않음 |
| 두 폰은 어떻게 구별하나요? | user_id·session_id·device로 대조. user_id는 앱 식별자이며 물리기기 영구 ID 보장과는 구분 |
| 각 계정의 DB는 어떻게 연결했나요? | Interface Endpoint→Endpoint Service→Internal NLB→MongoDB, TLS·계정 인증 |
| SSH 터널을 계속 켜야 하나요? | 서버 간 적재는 PrivateLink. 노트북 터널은 관리·조회용 |
| 늦은 이벤트는 언제 집계하나요? | event_time을 기준으로 설계. 실제 watermark·창 갱신 정책은 최종 코드 확인 필요 |
| S3·Delta Lake까지 완성했나요? | 현재 검증된 저장은 MongoDB. S3 샘플은 후속 통합, Delta 적용은 미확인 |
| 모델이 실제로 얼마나 정확한가요? | 현재 자료에 독립 평가셋 성능이 없어 정확도 수치 확정 전 |

## 발표 전 팀 확인

- 팀명, 이름, 역할, 프로젝트 기간, 각자 직접 구현한 범위.
- 최신 앱 빌드와 BaseURL, 시연용 키 주입, CA 파일과 서버 상태.
- 집계 컬렉션 이름, 정확한 통계 분모, 지연 이벤트 정책.
- 실제 전송 ID·응답과 DB 대조 화면, 키가 드러나지 않는 시연 자료.
- 모델·AIHub 본보기의 사용 조건과 공개 가능한 자료 범위.
