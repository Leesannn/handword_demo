# 구현 선택과 기술적 판단

팀이 사용한 구성을 문제·선택·효과·운영 특성으로 정리합니다. 앱 소스, 서버 담당자의 배포 보고, 실제 DB 수행 결과에 근거한 설명입니다.

| 선택 | 해결한 문제 | 적용 효과 | 운영 특성 |
|---|---|---|---|
| 기기 내 추론 | 단어 판정과 서버 통신의 결합 | 카메라 영상 업로드 없이 단어 판정 | iOS Core ML·Android JavaScript 엔진 |
| 파일 Outbox | 오프라인·응답 유실 | 같은 이벤트 ID로 재전송 | 파일 선저장·상태 가드·지수 백오프 |
| Kafka·Spark 분리 | API 수신과 통계 처리의 결합 | 발행 수락 후 비동기 소비 | 파티션·오프셋·체크포인트로 추적 |
| 원장·집계 분리 | 단건 추적과 통계 조회 | 원문 대조와 학습 지표 저장 | 개별 기록과 계산 결과의 역할 분리 |
| payload 문자열 보존 | 원천 내용 대조 | Kafka·DB의 ID·원문 비교 | 내부 속성 조회는 JSON 파싱 사용 |
| topic·offset 인덱스 | 최근 기록의 전체 스캔 | 최근·범위 조회 검사량 감소 | 인덱스 갱신과 저장 공간 사용 |
| PrivateLink·TLS | 별도 계정의 DB 연결 | 사설 서비스 경로와 인증 구성 | Endpoint·NLB·CA 관리 |
| Elastic IP | 중지·시작에 따른 주소 변경 | 고정 관리·앱 접속 주소 | 서버 간 MongoDB는 PrivateLink 경로 사용 |

## 서로 다른 식별자의 역할

Kafka의 user_id 키는 사용자 이벤트의 파티션 배치에, event_id는 개별 기록의 재전송 식별에 사용합니다. Kafka 오프셋은 파티션 안의 처리 위치입니다. 팀은 API 응답·이벤트 ID·Kafka 위치·DB 원문을 연결해 적재를 조사했습니다.

## 수락 시점의 분리

API는 Kafka 발행을 확인한 뒤 202를 반환합니다. MongoDB 저장은 Spark의 비동기 소비 단계에서 이뤄집니다. 이 구분을 기준으로 HTTP 수락 후 원장이 보이지 않았던 사례의 Spark 필터·출력 대상을 조사했습니다.

## 조회 최적화의 판단 근거

팀이 실제 추가한 인덱스는 { topic: 1, offset: -1 }입니다. 특정 토픽의 최근 기록과 증가분 조회에 맞춰 키 순서를 정했습니다. 73건의 원장에서 10건을 조회할 때 검사 문서가 73→10으로 줄었고, 반환 BSON과 순서를 비교해 원문이 같음을 확인했습니다.

시간 측정은 0~1ms였으므로 성과는 문서 검사량 감소와 별도 정렬 제거로 표현합니다.
