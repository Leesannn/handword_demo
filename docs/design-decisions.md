# 설계 결정과 트레이드오프

구현 선택을 문제, 선택, 효과, 한계로 정리합니다. 정식 의사결정 회의록이 제공되지 않은 항목은 자료에 드러난 구조에 대한 기술적 해석입니다.

| 결정 | 해결할 문제 | 선택의 효과 | 비용·검증 경계 |
|---|---|---|---|
| 기기 내 추론 | 카메라 판정과 서버 통신의 결합 | 서버 추론 응답 없이 단어 판정, 영상 전송 감소 | 기기 성능과 엔진 수치 동등성 평가 필요 |
| Outbox 선저장 | 연결 실패·응답 유실 | 같은 이벤트를 다시 전송 가능 | 중복 도착, 큐 상한과 파일 오류 처리 필요 |
| Kafka·Spark 분리 | 모바일 요청과 통계 계산의 결합 | 발행 수락과 집계 분리, 오프셋 기반 재처리 | 비동기 소비 지연과 보관 기간 관리 |
| 원장·집계 분리 | 개별 추적과 통계 조회 동시 지원 | 원문을 근거로 적재·통계 대조 | 여러 저장의 중간 실패 정합성 필요 |
| payload 문자열 보존 | Kafka 원문과 대조 | 이벤트 ID·원문 비교 가능 | 내부 속성의 검색·인덱싱에 파싱 필요 |
| topic·offset 인덱스 | 최근 조회의 전체 스캔·정렬 | 해당 조회의 검사 문서 감소 | 인덱스 갱신·저장 공간 추가 |
| PrivateLink 연결 | 별도 계정·VPC의 서비스 연결 | 사설 경로와 관리 SSH 구분 | Endpoint·NLB 비용·인증서 운영 |
| Elastic IP | 중지·시작 후 관리 주소 변경 | 고정 관리·앱 접속 주소 | 보유 중 IPv4 요금 고려 |
| S3 샘플 분리 계획 | 큰 좌표와 검색 메타데이터의 접근 차이 | 파일 다운로드와 목록 검색 분담 | 실제 통합·부분 실패·삭제 검증 필요 |

## 메시지 키와 이벤트 ID

Kafka 키는 user_id, DB 키는 event_id입니다. 전자는 사용자 이벤트를 같은 파티션으로 배치하는 데 사용하고 후자는 재전송된 개별 이벤트를 식별합니다. 파티션 변경·사용자 ID 재생성 등의 조건을 포함한 영구 순서 보장으로 확대 해석하지 않습니다.

## 202 응답의 책임 범위

서버는 Kafka 발행 확인 뒤 수락합니다. HTTP 응답이 유실되면 앱이 이미 발행된 이벤트를 다시 보낼 수 있습니다. 따라서 앱의 재전송, 원장 키 중복 방지, 집계 재실행 정책을 함께 다뤄야 합니다. 일부 이벤트만 발행된 배치의 실패도 추가 시험 대상입니다.

## 원장 보존과 조회 모델

현재 payload 문자열 보존은 원문 대조에 활용했습니다. 사용자·기기별 조회가 늘면 검색용 필드를 추출하거나 별도 조회 모델을 둘 수 있습니다. 이번 팀 작업에서 실제 추가한 것은 topic·offset 인덱스이며 검색 모델 마이그레이션은 수행하지 않았습니다.

## 체크포인트와 집계 정합성

체크포인트는 Spark의 소비 위치·상태 복구 기반입니다. 원장 저장 후 집계 쓰기 전에 종료되면 재실행 시 같은 입력을 다시 처리할 수 있습니다. 제공 자료에 중간 실패 시험이 없어 다중 컬렉션 원자성이나 전체 exactly-once 처리를 확정하지 않습니다.

## 현재 규모에서의 성능 설명

두 폰 동시 사용과 73건 원장의 인덱스 비교는 특정 조건의 검증입니다. 구성 요소가 Kafka·Spark라는 이유로 대규모 처리 실적을 주장하지 않습니다. 현재 성과는 실제 단말의 적재 확인과 실행 계획에 근거한 조회 개선입니다.
